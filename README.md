# qa-practice-e2e

Playwright + TypeScript end-to-end tests for **qa-practice-api** and **qa-practice-web**,
structured like a production E2E framework: generated API client, factories, setup projects,
fixtures and page objects.

## Run it

1. Start the API and the web app (see their READMEs), with the baseline seed loaded.
2. Here:

```powershell
npm ci
npx playwright install chromium
copy .env.example .env      # WEB_URL and API_URL

npm run e2e                 # reset the DB to the baseline, then run everything
npm run e2e:fast            # run without resetting (quick local iteration)
npm run test:smoke          # only @smoke tests
npm run test:ui             # Playwright UI mode
npm run report              # open the last HTML report
```

## Run lifecycle

`seed` → `auth` → `chromium`, as Playwright projects with dependencies:

1. **seed** (`setup/seed.setup.ts`) calls `GET /api/e2e/seed-status/` and fails fast with a clear message if the baseline is missing.
2. **auth** (`setup/auth.setup.ts`) logs in once per role (admin, viewer), saves the browser session to `src/tests/auth/users/<role>.json` and the API token + organisation id to `<role>.meta.json`.
3. **chromium** runs the specs, logged in as admin by default. A spec switches role with `test.use({ storageState: STORAGE_STATE.viewer })`.

## Structure

```
playwright.config.ts          projects, reporters, retries, artifacts
kubb.config.ts                OpenAPI → client, types, faker builders
bin/                          reset-db.mjs, download-schema.mjs
src/
├── @generated/               generated by Kubb, never edit by hand
├── config/                   env (dotenv), storage paths, API client per user
├── factories/                create test data through the API
└── tests/
    ├── setup/                seed check + auth per role
    ├── fixtures/             the single test.extend wiring point
    ├── pages/                page objects (base/, auth/, suppliers/)
    ├── specs/                tests, grouped by feature (auth/, suppliers/, api/)
    ├── messages/             expected UI text
    ├── snackbars/            expected notification texts
    ├── test-data/            users, countries
    └── auth/users/           saved sessions (git-ignored)
```

## Conventions

- Seed with the API (factories), act with the UI only for the behaviour under test.
- Specs get everything through fixtures; they never call `new SomePage()` or build HTTP requests.
- Page objects hold the locators, actions (`clickAddSupplier`) and checks (`verifySupplierRow`).
- Locators: roles and labels first, `data-testid` next; scoped to their container (a row by supplier name, a summary value by its label). No CSS chains, no positions in lists.
- Web-first assertions only, no `waitForTimeout`.
- Unique data (faker) and cleanup after each test (the `suppliers` fixture deletes what it created), so tests are parallel-safe.
- Tags: `@smoke` for the fast critical path, `@regression` for the rest.

## After an API change

```powershell
npm run types        # download the schema + regenerate src/@generated
npm run typecheck    # breaking changes show up as TypeScript errors
```
